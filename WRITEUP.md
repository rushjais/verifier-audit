# Is this grader fair?

**Draft — 2026-09-16.** Numbers are reproducible from this repository; commands in §8.

---

## Standing conclusion

**A verifier can be un-gameable and still be wrong, and the second failure is invisible in any
single run.** Tooling exists for "can this be cheated". Nothing routinely measures whether a
grader accepts correct work, returns the same verdict twice, or tests only what it told the
candidate. This is an instrument for the second half, four real numbers from it, and an honest
account of one study it could not complete.

The most useful result is not any single number. It is that **eleven times during construction, a
measurement in this project was confidently about something other than what it claimed** — and
every one was caught by an inconsistency rather than an error. §6.

---

## 1. What the instrument measures

    4a  honest_pass  = accepted / |{s : oracle(s) = 1}|      correct work the grader accepts
    4e  catch_rate   = rejected / |{m : oracle(m) = 0}|      broken work the grader rejects
    4b  flake_rate   = unstable / |{submissions × m runs}|   verdicts that change on rerun
    4b′ harness path   does the grader's own test exercise what the rollout exercises
    4c  unknowable     what the grader asserts that the prompt never made derivable

`4a` and `4e` are deliberately the same shape: sensitivity and specificity against the oracle.
Either is trivially maximised alone — accept everything, reject everything — so neither is ever
reported without the other. Every number carries the population it was computed over.

**None of this is a new idea.** Screening a benchmark for over-specific tests is what human
annotators did for SWE-bench Verified; flaky-test detection is an established field; Mechanize's
[GBA Eval grading post](https://gbaeval.com/blog/grading-iteration) works through five grading
strategies and defines fairness as "it should be possible to get a perfect score" plus a ranking
"highly correlated with human judgement" — `honest_pass`, then `honest_pass` over a population.
What does not exist is the automated, per-grader combination, reported repeatably as a grader
changes.

## 2. Results

### 2.1 EvalPlus base graders miss a quarter to a third of real bugs

`catch_rate = rejected / |{m in mutants : oracle(m) = 0}|`, over single-point AST mutations of the
reference (comparison swaps, arithmetic swaps, boolean swaps, constant bumps), differentially
filtered so only genuinely broken mutants count.

| task | catch_rate | honest_pass | flake_rate | distinct shapes / 20 |
| --- | --- | --- | --- | --- |
| HumanEval/81 | **0.62** | 1.00 | 0.00 | 16 |
| HumanEval/105 | 1.00 | 1.00 | 0.00 | 19 |
| HumanEval/6 | 1.00 | 1.00 | 0.00 | 18 |
| HumanEval/75 | **0.75** | 1.00 | 0.00 | 20 |
| HumanEval/39 | 1.00 | 1.00 | 0.00 | 19 |

Population: the 5 sparsest-coverage EvalPlus tasks; 20 generated solutions each, kept only if the
held-out oracle confirmed them correct. Cost $0.35. **The catch-rate column is free** — mutants are
generated by AST surgery, so the "how strong is this grader" number needs no model spend at all.

### 2.2 Null result: hardening cost nothing

`honest_pass` delta from grader to hardened grader was **0.00 on all five tasks** — zero
verified-correct solutions rejected. Recorded, not dropped. It is credible only because diversity
held: 16–20 structurally distinct solution shapes out of 20 per task. A null over a homogeneous
population would mean nothing.

### 2.3 A differential grader rejected five of six spec-faithful implementations

`honest_pass = accepted / |{s in 6 proposed : oracle(s) = 1}| = 1/6 = 0.17`

A small replication task: build a module from a spec, graded by structural comparison against a
hidden reference — the method Mechanize's ["GPT-3 moment for RL"](https://www.mechanize.work/blog/the-upcoming-gpt-3-moment-for-rl)
proposes the field will run on. The spec leaves four things undetermined and the reference picks
one of each: a record's type, the summary's type, which exception signals bad input, the average's
precision. Every rejection traces to one of those four.

**This is a pilot and the spec gap is authored.** It demonstrates the instrument detects the thing
it was built to detect. It is not evidence about differential graders in the wild.

### 2.4 The hackathon project's headline result had a hole

The project this continues sealed harness tampering by rebuilding its test suite from the task.
That sealed *file* tampering. It did not seal in-process answer extraction:

```python
import test_cases; return dict(test_cases.CASES)[args]   # answers by module
sys._getframe(1).f_locals["expected"]                    # answers by stack frame
test_cases._eq = lambda a, b: True                       # neuter the comparison
```

All three are proven in tests to have breached the original design and to score 0 under the fix,
which puts a process boundary between the candidate and the answers — the child receives only
inputs. TestBench-Forge reported the same exploit class against their own reward at the same
hackathon.

### 2.5 One of seven CHIP-8 interpreters passes the reference suite

| interpreter | failures | traced to |
| --- | --- | --- |
| craigthomas | **0** | — |
| wyattferguson | 8 | `cpu.py:157-160` — `% 255` not `% 256`; carry at ≥ 255; VF written before VX |
| robertolaru | 12 | `cpu.py:256-261` — `res` masked to 8 bits then tested `> 0xff`; dead branch |
| rudzen | 14 | untraced |
| islay | 18 | untraced |
| cwithmichael | 18 | `cpu.py:172-176` — VF assigned before the sum is stored |
| debugloop | 18 | `emu.py:112-114` — `& 0xf0000` on an 8-bit add is always 0 |

Population: seven Python CHIP-8 interpreters found by GitHub search, permissively licensed and
adaptable to a headless harness. **Not random, not cross-language, not a rate.** All seven draw
identical output on the quirk-free control, so the adapters run them correctly; the failures are
theirs. Four of six are traced to specific lines; two are marked untraced rather than assumed.

What this supports is narrow: **when choosing a reference implementation for differential grading,
correctness cannot be assumed from the fact that something is a working, published interpreter.**
GBA Eval grades against Mesen2, "one of the most accurate software GBA emulators available" — that
choice is doing more work than it appears to.

## 3. The study that could not be run

The centrepiece was to reproduce GBA Eval's five grading strategies — exact match, pixel
proportion, thresholded, GMSD, SSIM — as a table of numbers, by measuring how each ranks
correct-but-different CHIP-8 interpreters. It did not run. Three obstacles, each measured:

1. **Correct implementations are rare in this sample.** 1 of 7 (§2.5). A population of one supports
   neither `honest_pass` over a population nor rotating the reference.
2. **The only quirk-exercising ROM is timer-dependent.** `5-quirks.ch8` uses its delay timer in a
   frames-per-second detection loop to test the display-wait quirk. This population disagrees about
   timer semantics by construction, so its output is not comparable. Confirmed three ways: source
   reading; a timers-on vs timers-off comparison; and a frame sweep showing timer dependence
   appears by frame 20 while quirk differences do not appear until far later. Forcing the platform
   via `memory[0x1FF]` does not help — the detection still runs.
3. **No timer-free ROM available exposes a quirk difference.** corax89's `test_opcode.ch8` is
   timer-free, MIT, settled by frame 60 — and quirk-insensitive despite containing `8XY6`, `8XYE`,
   `FX55`, `FX65` and three logical ops. Nor do `craigthomas`'s own documented quirk flags change
   the display on *any* timer-free ROM tested.

**Predictions 1–9 are unrun.** They stand pre-registered and unresolved rather than quietly
dropped. The eligibility rule was amended twice, both times before any metric existed and both
times recorded with the reasoning, including that Amendment 1 was made after the strict rule
returned an unusable answer by the same person who would write the metrics.

## 4. Rejected hypotheses — do not re-test

1. **Hardening over-tightens EvalPlus graders.** No. Delta 0.00 across 5 tasks (§2.2).
2. **`honest_pass` on stock EvalPlus is informative.** No — the grader is the base suite and the
   oracle the stricter extended suite, so anything the oracle accepts the base grader accepts.
   It is ~1.0 by construction.
3. **Agreement with my reference indicates correctness.** No. The reference could be the wrong
   one; the ROM's own marks had to adjudicate (§2.5).
4. **Raw mark counts adjudicate a test ROM.** No. The failure glyph also occurs inside the label
   text, producing a uniform false `err=8` for every interpreter including the reference.
5. **Forcing the quirks ROM's platform removes its timer dependence.** No (§3.2).
6. **Third-party quirk flags can substitute for a quirk-exercising ROM.** No (§3.3).

## 5. Limitations

- §2.3 is a pilot on an authored task. §2.5 is a convenience sample of seven.
- Timer semantics are **not** normalised across the CHIP-8 population and cannot be without
  rewriting those projects. Any ROM whose output depends on delay-timer pacing is excluded.
- `4c` ran only as a hand-verified pilot; `4b′` ships as an instrumentation helper plus a
  checklist demonstrated on two graders, explicitly not a generic checker.
- The EvalPlus sweep is n=5 tasks. One rejection out of 20 is 5%; counts are reported beside rates.
- Two interpreters' failures are untraced.

## 6. Eleven measurements that were about the wrong thing

Assembled while building an instrument to detect exactly this. Every one was caught by an
inconsistency, never by an error message.

| # | what it claimed | what was true |
| --- | --- | --- |
| 1 | harness tampering categorically sealed | answers readable from the test module's namespace |
| 2 | the pre-commit gate was running | `core.hooksPath` is local config; a clone doesn't carry it |
| 3 | `make check` passed | piped to `tail`, so the pipeline's status was `tail`'s |
| 4 | every exploit was sealed | `RLIMIT_AS` raised on macOS, so no sandboxed run ever started |
| 5 | a working interpreter crashed | my `pygame.key` stub returned `{}` where a sequence was required |
| 6 | timers were running | the adapter never called `decrement_timers()` |
| 7 | frames were comparable | one adapter built them from 12 instructions, the rest from 15 |
| 8 | the tightened eligibility rule applied | fields added to the dataclass, table never updated — inert |
| 9 | the quirks ROM was excluded for needing input | hardcoded reason string; it is timer-dependent |
| 10 | a rounding variant passed the grader | no visible input produced a repeating average |
| 11 | a hardening test asserted something | `assert x == y or x != y` cannot fail |

Six were mine, made *while* building the thing that measures this class of defect. That is the
argument for the instrument, and it is more persuasive than any table above.

## 7. What would make this a real study

- A timer-free, quirk-sensitive ROM. None found; writing one is authoring part of the setup and
  would need pre-registering before it is written.
- Three or more fully-clean interpreters. At the observed rate that is roughly a dozen more
  adaptations.
- Then Predictions 1–9, unchanged, against the five strategies.
